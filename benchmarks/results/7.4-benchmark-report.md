# Task 7.4 — the benchmark report

**In progress.** B1, B2 and the first optimisation are measured and recorded below. Connection
scaling (B3 re-measured), market quality under load, the `trace` tool and the plots are still to
come, and this file says so rather than leaving a reader to guess which sections are evidence.

Goal 5 asks for measured performance instead of unsupported claims, and Open Issue 012 §1 puts
the difficulty precisely: *the hard part is not making the system fast, it is measuring it in a
way that survives scrutiny.* So the methodology comes before the numbers, and §6 — what was not
tested — is not an afterthought.

---

## 1. Methodology

### Coordinated omission, and how it was avoided

The standard load generator sends a request, waits for the response, and sends the next. If the
system stalls for 200 ms the generator stalls too, never issues the requests that *would have
arrived* during the stall, and never records their latency. The stall vanishes from the
measurement and p99 looks excellent.

`benchmarks/bench_e2e.py` is open loop. Every send time is computed before the run starts, as
`t0 + i / rate`; one task per order fires at its own instant regardless of what any other order
is doing; and **latency is measured from the intended send time, not the actual one**. When the
gateway slows, nothing here slows with it — the in-flight count grows and the measurement shows
it.

That guarantee is only as good as the harness's own punctuality, so `send_slip` — intended send
time to actual send time — is measured and reported at every rate. It is the reader's check on
whether a row describes the exchange or describes Python's event loop. **Rows where slip is
large are marked and not quoted.**

### Distributions, never averages

Every figure below is p50/p95/p99/p99.9/max by nearest rank on the sorted samples, so each
number printed is a latency that actually happened to some order. No mean appears in this
document.

### Warm-up

Five seconds discarded at every rate in B2; 20,000 orders per workload in B1. Cold pages, a cold
allocator and Redis AOF behaviour all differ during that interval.

### Topology — read this before any B2 number

**Everything ran on one laptop:** gateway, matcher, ledger, fan-out, archiver, bots, Redis,
PostgreSQL, the market bots' order flow, and the benchmark harness itself, all sharing ten cores.
Task 7.4's Boundaries call for a scratch deployment; there is no scratch deployment, because
Task 3.3's deployment half is on hold pending a deployment target. This is stated here rather
than worked around, and it is the first entry in §6.

The effect is not uniform. Serialisation counts and per-hop *orderings* are exact. Tail latencies
are pessimistic — processes that would not compete for cores in a real deployment are competing
here. The knee in §3 is therefore a property of this host, not of the design.

## 2. B1 — the native engine

Pure C++ against the shipped order book: no Python, no Redis, no network. 200,000 orders per
workload after 20,000 discarded.

    g++ -std=c++20 -O2 -Wall -Wextra -Werror -I. -o bench engine/cpp/order_book.cpp engine/cpp/bench_order_book.cpp
    ./bench --orders 200000 --warmup 20000

"Orders per second" is meaningless without saying which orders, so there are three workloads:
`rest` never crosses and measures book growth, `cross` crosses every time and measures the
matching path, `mixed` walks a mid with roughly one order in eight priced through the spread.

Per-order cost, nanoseconds:

| workload | fills | p50 | p95 | p99 | p99.9 | max | orders/sec |
|---|---|---|---|---|---|---|---|
| rest | 0 | 292 | 750 | 1,791 | 5,750 | 675,667 | 2,637,581 |
| cross | 181,522 | 166 | 375 | 500 | 625 | 13,209 | 6,054,069 |
| mixed | 158,379 | 125 | 1,041 | 1,500 | 2,708 | 19,708 | 3,117,118 |

The harness measures its own clock too, because the quantity being timed is close to the cost of
timing it: two back-to-back `steady_clock::now()` calls cost a p50 of 42 ns locally, and inside
the container the timer is quantised to ~41.7 ns. Every per-order figure above should be read as
carrying that granularity.

**Matching costs ~166 ns at the median**, against the ~1 µs Open Issue 012 §3 budgeted. The
engine is faster than its own design estimate by a factor of six.

## 3. B2 — end to end, HTTP in, WebSocket out

Load is dealt round-robin across eight accounts, because `max_orders_per_second` is 1,000 per
user and a single-account ramp would measure the rate limiter. `429`s are counted, never retried
— a retry would reintroduce coordinated omission through the side door. Probe orders rest one
tick above zero so they never trade, keeping the fill path out of a measurement about the
request path.

### The knee

Coarse ramp, 20 s measured after 5 s warm-up, milliseconds:

| rate | accepted | errors | ack p50 | ack p99 | priv p50 | slip p99 | |
|---|---|---|---|---|---|---|---|
| 100 | 2,000 | 0 | 5.13 | 13.31 | 28.24 | 1.04 | |
| 200 | 4,000 | 0 | 4.71 | 190.10 | 31.35 | 4.09 | |
| 400 | 8,000 | 0 | 9.78 | 1,436.58 | 46.68 | 134.26 | soft — slip is 9% of p99 |
| 800 | 14,788 | 126 | 81,931 | 161,264 | 86,058 | 2,928 | **not evidence** |

The 800/s row is discarded. A `send_slip` p99 of 2.9 s means the harness was that late onto the
wire, so the row measures this event loop. The mechanism is worth recording because it bounds
single-process open-loop generation generally: when the server slows, tens of thousands of
pending tasks crowd the event loop's ready queue and delay the wakeups of orders that have *not
yet been sent*, so server slowness leaks backwards into the send schedule. Above roughly 300/s on
this host, load has to come from more than one process to stay honest.

Fine ramp where slip stays under 3 ms throughout, and is therefore quotable:

| rate | ack p50 | ack p99 | ack max | priv p50 | ptail p50 | slip p99 |
|---|---|---|---|---|---|---|
| 150 | 5.04 | 54.66 | 121.10 | 35.07 | 32.60 | 1.05 |
| 200 | 4.38 | 12.57 | 35.95 | 33.38 | 31.13 | 0.97 |
| 250 | 6.22 | 83.14 | 165.75 | 37.75 | 33.38 | 1.69 |
| 300 | 6.88 | 262.79 | 366.07 | 41.79 | 36.41 | 2.71 |

The median is flat at 4.4–6.9 ms while p99 climbs from 12.6 to 262.8 ms. A stable median with a
degrading tail is queueing onset: **the knee is between 200 and 300 orders/sec on this host.**

These four rows are single runs. Run-to-run variance is visible in them — 200/s scoring a better
p99 than 150/s is noise, not a finding — and the repeated runs that would let a tail be quoted
with confidence are listed in §6.

### What saturated first

Container CPU sampled once per second through the fine ramp, as a percentage of one core:

| process | median | p90 | max |
|---|---|---|---|
| **ledger** | **77.0** | **109.4** | 121.2 |
| gateway | 45.5 | 85.3 | 150.6 |
| fan-out | 14.8 | 27.3 | 38.4 |
| matcher | 12.7 | 45.5 | 73.5 |
| Redis | 9.2 | 15.5 | 107.5 |

The ledger — the derived read model, not the order path — is the process closest to saturating a
core, and it is the first thing to fix if this host's knee needs raising. It is worth being
precise about what that does and does not mean: the ledger is a *consumer*, so its lag does not
delay an acknowledgement. It competes for CPU with everything else on this one machine, which is
exactly the single-host artefact §1 warned about, and on separated hosts it would not.

## 4. The measured latency budget

Anchored on the stream itself rather than on an added tracing layer: the acknowledgement carries
`seq`, the inbound stream id, and every frame the exchange sends back carries the timestamp
needed to time its own path (Open Issue 012 §5 — the event stream already is the trace).

Per-hop, at 150–300 orders/sec, medians:

| Stage | Expected (012 §3) | Measured | |
|---|---|---|---|
| HTTP parse, auth, validation, risk, `XADD` | ~310 µs | **1.7–5.1 ms** | direct probe, five trials |
| Matching | ~1 µs | **166 ns** | B1, `cross` p50 |
| Inbound append → outbound append (engine hop) | ~150 µs | **1 ms** | direct probe, five trials |
| Outbound append → private frame at the client | ~50 µs | **~30 ms → 3.4 ms** | see §5 |

Two findings, both of which the design predicted in direction and missed in size:

1. **Matching is ~0.0005% of what a trader waits for** — 166 ns inside a ~31 ms path before §5's
   change, and inside a ~5.5 ms path after it. Open Issue 012 guessed 0.002%. The component
   optimised hardest is, by a wider margin than anyone estimated, the one that matters least.
2. **The 20 Hz conflation window dominated everything else** — and it dominated a path that the
   design had explicitly exempted from conflation. That is §5.

The gateway hop is the one the budget under-estimated, by roughly an order of magnitude: 1.7–5.1
ms measured against ~310 µs expected. It has not been decomposed further, and until it is,
nothing here says which of parse, auth, risk or `XADD` owns it.

## 5. The optimisation — private frames no longer wait for the tick

**Before.** Open Issue 006 settles that private data is never dropped and is not conflated. The
implementation honoured the first half: `offer_private()` appended the frame to a deque, and the
20 Hz `flush()` handed it to the writer. So an acknowledgement or a fill waited a uniform
nought-to-fifty milliseconds — a 25 ms median — for a tick it had been exempted from. Never
dropped, but always waited. B2 found it: `ptail`, the span from durable append to the frame
landing on the client, sat at a flat ~31 ms at every rate, which is the signature of a fixed
wait rather than queueing.

**The change.** `offer_private()` hands over immediately. Market frames still wait for the tick,
which is what conflation is for — they are superseded, so batching them is free — while a private
frame is never superseded and there is nothing to gain by holding it.

**After.** Identical rates, 15 s after a 5 s warm-up, eight accounts, milliseconds:

| rate | ptail p50 before | after | priv p50 before | after | priv p99 before | after |
|---|---|---|---|---|---|---|
| 150 | 32.60 | **3.41** | 35.07 | **5.62** | 98.38 | **22.71** |
| 200 | 31.13 | **3.77** | 33.38 | **6.53** | 59.11 | **42.01** |
| 250 | 33.38 | **3.65** | 37.75 | **6.15** | 116.03 | **71.77** |
| 300 | 36.41 | **3.40** | 41.79 | **5.50** | 308.43 | **28.90** |

Roughly nine times faster at the median, and at 300/s an order of magnitude off the tail. The
tail had been growing with load because private writes queued behind ticks; it no longer does.

**What the change cost, re-measured rather than assumed.** Task 5.2's own success criteria:

- *Criterion 5 — serialisation happens once per symbol per tick.* 5.726 encodes/tick at 1
  client, 5.851 at 50, 5.926 at 200. Flat in the client count, which is the property claimed.
- *Criterion 1 — 200 clients without acknowledgement latency degrading.* 3.80 ms median loaded
  against 3.95 ms quiet; the loaded case measured faster, as it did when 5.2 was first recorded.
- `tests/fanout` passes, 78 tests.

One trade, in policy and stated rather than buried: at 200 clients, frames delivered now spread
1178/1183/1191 where they were previously identical across clients. A market frame offered while
a private write is in flight is skipped for that tick — the documented slow-client policy, safe
because complete snapshots mean the next frame repairs it, and the same property that made
skipping affordable to begin with. It is a 1% spread and nobody is starved.

## 6. Limitations — what was not tested, and what these numbers do not support

- **No separated-host topology.** Everything shares ten cores with the harness. Task 7.4's
  Boundaries ask for a scratch deployment and there is none, because Task 3.3 is on hold pending
  a deployment target. Tails are pessimistic; the §3 knee belongs to this host.
- **Single runs.** The ramps in §3 are one run each, and run-to-run variance is visible in them.
  Task 2.1 reported medians of three runs; these tables do not yet, so no tail here should be
  quoted as *the* tail.
- **Nothing above ~300 orders/sec has been measured honestly.** The harness, not the exchange,
  is the limit above that, and the fix is multi-process generation rather than a bigger number.
- **B3 has not been re-measured since the §5 change.** The 200-client figures above come from
  `bench_fanout.py`, which is Task 5.2's harness; connection scaling to the point where update
  delay degrades is still to do.
- **Market quality under load is not measured.** Spread, depth and market-maker obligation
  compliance as throughput rises are a deliverable of this task and are not in this document.
- **Recovery time is not measured here.** A fan-out restart replaying 2,001,581 outbound records
  took about 30 seconds, observed once in passing while deploying §5's change. That is an
  anecdote, not a measurement, and it is recorded as one.
- **The gateway hop is not decomposed.** §4 shows 1.7–5.1 ms for everything up to and including
  the durable append; which part owns it is unknown.
- **`book_delay`, printed by the harness, is not quoted in this document and should not be.** It
  computes receipt minus the `seq` on the arriving L2 frame, but that `seq` is the *newest*
  record folded into the snapshot, so it measures time since the last update before the tick
  rather than any particular order's conflation wait. An honest public-path conflation figure
  needs the order's own outbound id and the first frame at or past it. The column stays in the
  tool's output because removing it would hide that the bias exists; it is fixed alongside the
  `trace` tool, which needs the same lookup.
- **The engine's own C++ tests, and the differential test against the naive model, are not
  performance evidence** and nothing here re-verifies correctness under load.
