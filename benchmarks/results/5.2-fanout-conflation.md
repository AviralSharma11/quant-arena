# Task 5.2 — fan-out under two hundred clients, measured

**Recorded 2026-09-05.** Reproduce with `python benchmarks/bench_fanout.py --clients 200`.

Machine: Apple M4 · 10 cores · 16 GB · macOS 26.6.2 (Darwin 25.6.0) · Redis 7.4.11 (container) ·
Python 3.13.9.

**Topology caveat, stated first because it bounds every number below.** Docker Hub was
unreachable while this was measured, so the fan-out image could not be built. Redis, PostgreSQL,
the matcher and the ledger ran in containers; the gateway and fan-out ran on the host against
them. Every process, all two hundred WebSocket clients, and the benchmark harness itself
therefore shared ten cores on one laptop. That makes the tail latencies below *pessimistic* — the
contention they show is between processes that in deployment would not be competing for the same
cores — and it does not affect the serialisation counts at all, which are exact.

## The two questions

Success Criterion 1 is about **the gateway**, not about fan-out:

> Two hundred or more concurrent clients receive updates without gateway acknowledgement latency
> degrading measurably.

That is the check on Open Issue 006 §7b, which made fan-out a separate process precisely so that
connection load could not reach the order path. So the harness samples order acknowledgement
latency with nobody connected, opens two hundred WebSockets to fan-out, and samples again — with
a background account churning ~110 orders/sec throughout **both** samples, so the only difference
between them is how many browsers are attached.

Success Criterion 5 is fan-out's own, and is a ratio rather than a duration:

> Serialisation happens once per symbol per tick, verified by instrumentation.

`Hub.encode` is the only place a message becomes a string and it counts; `/health` exposes the
counter. If encoding were per subscriber this number would scale with the client count.

## Criterion 5 — serialisation does not scale with clients

Ten seconds of feed, two symbols quoting, `book:*:l2` and `tape:*` subscribed.

| Clients | Ticks | Serialisations | Encodes/tick | Frames each client received | Messages delivered |
|---|---|---|---|---|---|
| 1 | 200 | **400** | 2.00 | 400 | 400 |
| 50 | 201 | **400** | 1.99 | 400 | 20,000 |
| 200 | 201 | **400** | 1.99 | 400 | 80,000 |

Flat. Two hundred times the delivery from the same four hundred encodes, and 1.99 encodes per
tick is exactly the two active symbols' L2 channels once each — the tape was quiet in these runs
because the churn rests its orders rather than crossing them.

`frames_min`, `frames_median` and `frames_max` were **identical** in every run at every client
count. Nobody was starved and nobody was favoured.

## Criterion 1 — acknowledgement latency at 200 clients

Four runs, 200 sequential order acknowledgements sampled per case. Median across runs.

| | No clients | 200 clients | Change |
|---|---|---|---|
| median | 3.50 ms | 3.65 ms | **+4.2%** |
| p95 | 4.62 ms | 6.36 ms | +38% |
| max | 7.51 ms | 10.52 ms | +40% |

The median is the honest headline: two hundred concurrent WebSocket clients cost the order path
about **150 microseconds**, which is inside this machine's run-to-run noise — one run measured
the loaded median as *faster* than the quiet one.

The tail is where the caveat at the top matters. p95 and max both rise, and on a single laptop
running six processes plus the harness that is what CPU contention looks like rather than
anything structural: fan-out never touches the gateway, never writes to the inbound stream, and
never holds a lock the order path can wait on. The number to re-measure at Task 7.4 is this
tail, on separated hosts.

Fan-out's own tick stayed at **1.7–2.7 ms worst case** against a 50 ms budget, at 200 clients.

## What this found

Two defects, neither of which the test suite could have found — both needed two hundred real
sockets:

1. **The session-lookup pool exhausted at 73 of 200 connections.** Two hundred browsers
   reconnecting at once — a fan-out restart, or a laptop waking — is two hundred simultaneous
   session `GET`s, and redis-py's default pool *raises* `MaxConnectionsError` rather than
   queueing. Seventy-three clients were told to go away because other clients were connecting.
   Fixed with a `BlockingConnectionPool`: a session lookup is one GET on the same machine, so
   waiting a few milliseconds behind other lookups is invisible, and failing is a dead feed.

2. **The harness's own churn was silently 401.** `POST /auth/register` does not set a session
   cookie, and the first version of the script only logged in when registration returned 409.
   Every churn order was refused, the book never moved, and the benchmark cheerfully reported a
   healthy feed at 0.09 encodes per tick. Recorded here because the failure mode is the
   dangerous one: a benchmark that measures nothing looks exactly like a benchmark that passes.

## What is not measured here

- **The slow-client policy.** Success Criterion 2 is proved in `tests/fanout/test_conflation.py`
  against a socket that accepts a write and never completes it, which is a more faithful stalled
  browser than a sleep and does not make the suite take eight seconds to say so.
- **A separated-host topology.** See the caveat above; the tail numbers deserve re-measuring for
  the Task 7.4 report.
- **Ten symbols.** The symbol table is provisional until Task 5.1, so this ran on two. The encode
  count is per active symbol per tick, so ten symbols is ten times four hundred — still
  independent of the client count, which is the property being claimed.
